### 决策

| 问题 | 结论 | 理由 |
|---|---|---|
| 扫码登录放哪 | 新建 `Pek.Wechat`（crate `pek-wechat`）库 | 微信业务语义（Sns 模型、授权流程）不属基础库；生态惯例是"业务库 + 依赖 dhrust" |
| 企业微信推送是否合并 | **不复制**：`pek-wechat` `pub use dhrust::wecom;` | 实现已存在于 DH.RustBase；复制会产生两份实现（违反"同一逻辑出现第二份就下沉"） |
| 哪些公共方法下沉 | `dhrust::web::url_with_query`；`dhrust::wecom::{send_text_blocking,send_markdown_blocking,send_value_blocking}` | 前者是通用 URL 拼接（片段保持在末尾，适用于任何授权跳转）；后者补齐阻塞上下文入口，与既有 `send_markdown_v2_blocking` 对齐 |
| 什么**不**下沉 | `WechatClient`、Sns 模型、账号选择、令牌缓存 | 只有单一消费方；微信专属刷新语义（`expires_in - 120s`） |
| 配置形态 | TOML `Config/Wechat.toml`，`[[Accounts]]` 多账号 | 与 Pek.RSms/Pek.RMail 一致；`TomlConfig` 负责补齐/迁移/热加载/注释保留 |
| 同步还是异步 | 同步 API（`blocking_request_with_retry`，tokio 内自动 offthread） | 与生态其他库一致；库不引入异步运行时 |
| 静默授权 | `login_with_user_info` 在 `/sns/userinfo` 失败时不视为登录失败（`user=None` + `user_info_error`） | `snsapi_base` 拿不到资料是微信既定行为，不应让登录整体失败 |
| 凭据处理 | `AppSecret`/`access_token`/`refresh_token`/`session_key` 的 `Debug` 一律脱敏 | 用户既有口径：凭据不明文落盘/进日志 |
